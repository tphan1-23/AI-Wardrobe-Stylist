## What the tests cover

- Input validation (email, name, household name, invite code, location) including boundaries and malicious-looking input; every sign-up password rule (length 8–72, uppercase, lowercase, number, symbol), and that log-in keeps the basic rule so older accounts still work.
- Every success and failure path of sign-up, log-in, log-out, create household, join household, leave household, save location and overview loading (including the members list), with the server replaced by an in-memory fake.
- Password reset: requesting a code, checking the code and setting the new password under the sign-up rules, with a wrong code never changing the password.
- Google and Apple sign-in: parsing the redirect Supabase sends back, refusing redirects that are not back to this app, cancel versus error handling, and saving the name Apple shares only once.
- The onboarding state machine: location, then ready; a household is optional.
- The Supabase adapter: correct RPC names and argument names, queries scoped to the signed-in user's own row, errors never returning data.
- Error mapping to friendly messages, and network failures.

## What is not covered, and why

- React Native screens (`AuthScreen`, `HomeScreen`, household screens) and `useSession` are not unit-tested: they need a device or emulator. They contain no business logic; the logic lives in the files above.
- `frontend/src/services/supabase.ts` (real client construction) is not covered for the same reason.
- No test talks to a real Supabase project. `tests/migration.test.ts` checks the SQL text of both migrations (tag lists, RLS on every table, owner-only write policies, `leave_household`). The migrations were also executed once by hand on in-memory Postgres (PGlite) with stand-ins for Supabase's `auth` and `storage` schemas, exercising sharing, leaving and permissions as real users; that check is not part of the automated suite.
